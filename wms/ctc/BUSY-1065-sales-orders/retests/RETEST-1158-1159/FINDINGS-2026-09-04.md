## Bug report

**Shell truncation printed unredacted customer PII to the session's own tool output.** During slice
R1, a command intended to safely preview a CloudWatch log line used `cut -c1-250` to cap output length.
The underlying log messages contained embedded newlines (pretty-printed JSON), so `cut -c1-250`
capped each *newline-delimited segment* rather than the logical message as a whole, and a full,
multi-line customer record (name, email, shipping address) printed in full before this was caught.

- **Not written to any file, result, or `STATE.md`.** Caught and corrected mid-task, before the content
  was reproduced anywhere else.
- **Root cause**: `cut -c` (and `head -c`, same problem) is not a safe truncation method against
  multi-line log content. The fix used for the rest of the session was a Python-based extraction that
  parses the message and prints only named, non-PII fields.
- **This has already been written into the plan's own rules**: `R3-update-semantics-no-cin7-write.md`
  carries a "Data handling" section verbatim because of this incident: *"Do not use `cut -c`, `head -c`
  or any width-based truncation as redaction on log output. Select fields explicitly with `--query` or
  `jq` and print only those. Width truncation on a line containing customer data prints customer
  data."* Recommend this rule get promoted into `CLAUDE.md` itself (currently only in one slice file)
  so every future session inherits it, not just ones that happen to read R3.
- Filed as internal product feedback separately (a Claude Code tooling gap: shell truncation is an
  unsafe redaction primitive against multi-line content generally, not specific to this codebase).

### R1, faulty sale worker ground truth (Q27) — TC4f FAIL (expected), everything else nuanced

TC4f fails, as R0 already predicted (no split exists). The real work was Q27's second half: does the
lambda "cannot execute... fields absent," or does it actually run?

- **MEASURED**: the queue-handler synchronously invokes a second, previously unexamined function

- **Write side, bus: MEASURED negative.** `staging-inventory-bus` has a catch-all log; confirmed active

  presence or absence — this is a real, unresolved gap, not a settled answer either way.
- TC4c re-confirms R0's wiring exactly (plus the new `cancel-order` family, nothing else new). TC4d
  stays INCONCLUSIVE (no guard line, no `pickslipUrl`, same standoff as before, even though the code

### R9, fixture watcher — built, and it hit immediately

Built `scripts/watch-for-fixtures.sh` (five checks, read only, no writes anywhere). First run:

- **Check 1 (second revision on an already-sent order): 69 of 70 hits.** Nearly every CTC order this
  plan has ever sent has since progressed to `Dispatched` in Cin7. **Spot-checked one for actual
  content** (`261115`): same SKUs, same count, no line/quantity/address diff — **this is a stage
  progression, not a content edit.** So it proves R3's actual scope (does a second sighting correctly
  no-op) but does not yet prove a TC4-shaped fixture (a genuine edit) exists.
- **Check 2 (cancelled/voided): 0.**
- **Checks 3-5 (repeated option code, item-master-absent SKU, over-25-char reference): each found a
  real, fresh, never-touched-by-us candidate**, but every one had already progressed to `Dispatched` by
  the time it was found — real, but past the stage window the poller can still create from. The script
  now tags every hit `ELIGIBLE` or `PAST` for exactly this reason.
- **Side findings**: zero CTC shipments in our own table are allocated to store `51908` — independent
  corroboration that wholesale orders never reach `staging-shipments` at all. Also established a fact
  worth keeping: Cin7's `reference` filter needs a literal `#` prefix for *every* reference shape, not
  just numeric-looking ones (confirmed against both a numeric and an alpha reference).

### R3, update semantics (no Cin7 write) — stopped, no cases run

pattern, not two unrelated incidents — something was generating heavy order volume in this shared
environment at the time.
